# Agent Note: 中转站不可信：token 与敏感信息的分层防护

Status: proposed

## Problem

用户以后会接更多中转站。很多中转站不可信，会盗用用户的 token 或窃取敏感信息。两种偷法：

- **偷 token**：中转站收到请求里的 Authorization key 后复制下来自己用。若该 key 是用户在官方平台的 key，中转站拿去就能直接调官方 API，等于盗用用户额度。
- **偷内容**：用户消息里的敏感信息（密钥、连接串、个人隐私、登录密码）原文发给中转站，中转站可留存。

## Proposal

先承认一个前提再谈防护：**bearer token 的本质就是「谁拿到谁就能用」**。中转站要替用户调模型，就必须拿到 key，拿到就能复制；模型要回答，就必须看到消息内容。完全解决不存在，只能分层降低风险：

1. **密钥隔离**：每个中转站用不同的 key，绝不复用；官方平台的 key 不交给中转站做转发（中转站只用自己发的 key）。
2. **脱敏**：发往中转前按规则打码，回复再还原（见 [upstream-redaction-before-relay](../feature/2026-11-16-upstream-redaction-before-relay.md)）。
3. **登录凭据走表单**：网站登录密码进加密存储、浏览器直接填，不进模型上下文（见 [website-login-credentials-vault-form](../feature/2026-11-16-website-login-credentials-vault-form.md)）。
4. **用量监控告警**：按连接统计请求量与 token 消耗，用量突然暴涨就告警（可能是 key 被盗用）。
5. **能直连官方就直连**：不经过中转时，暴露面最小。

## Alternatives considered

- **完全信任中转站** — 零成本；但中转站已出过 401 密钥失效、503 等问题，不可信是既成事实。
- **不用任何中转站，只调官方** — 最安全；但失去中转站的价格与可达性，用户明确要接更多中转站。
- **把 key 放在客户端、每次现取现用** — 缩小服务端留存；但请求仍须经过中转站，偷 key 的问题没解决。

## Acceptance criteria

- 同一个 key 不出现在两个连接里（新建连接时提示复用）。
- 异常用量有告警。
- 敏感内容默认脱敏（见脱敏提案）。

## Risks

- 脱敏只能挡住规则命中的内容，自然语言里的隐私（地址、行程）拦不住。
- 用量告警是事后发现，偷用发生后才能止损，止损靠换 key。
- 任何防护都挡不住「用户自己把官方 key 交给中转站转发」的用法，只能靠提示与默认值引导。
