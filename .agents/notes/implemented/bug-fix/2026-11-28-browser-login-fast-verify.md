# Agent Note: 导航结果直接给登录态，省掉登录后的重复验证

Status: implemented

## Problem

一次真实登录走了约 14 分钟。慢的原因之一在验证环节：浏览器确认登录后，模型又用 shell curl 做了一轮重复验证；而且登录态要模型自己从快照树里判断，多走了几步。导航结果里本来只有失败信号（`isLoginPage` + Cookie 未登录提示），没有成功信号：注入 Cookie 后登上了，模型也只能自己扫整棵树找退出按钮来确认。

重复验证是模型行为，不是代码写死的步骤——模型不确定才去复核。所以根治办法是让导航结果直接把登录态说清楚，而不是多写一道禁止复核的规矩。

## Decision

只改 `packages/adapters/src/browser-tools.ts`（服务端 adapter，不动 computer 镜像、不动 Cookie 注入、不动登录流程）：

- 新增导出的 `isSignedInPage`，是 `isLoginPage` 的正向镜像：导航结果的快照树或元素里出现退出控件（链接或按钮，名字整体匹配 `Log out` / `Sign out` / `退出登录` / `登出` / `注销` / `退出`）即判定已登录。
- `browserNavigateFromTool` 里，注入了 Cookie 且不是登录页、且 `isSignedInPage` 为真时，结果附一条提示：“已用保存的 Cookie 登录，页面有退出控件；以此为准，不用再用 shell 命令或快照重复验证登录。”
- 失败分支保持优先：页面同时像登录页又像已登录时，仍按“未登录”处理（误判未登录只会多一次登录尝试，误判已登录会让机器人跳过一次必须的登录）。
- 看不出结论时不附任何提示，模型按原来的方式从快照判断，行为与改动前完全一致。

只认退出控件、不认个人中心类链接，是故意的：未登录的页面也可能挂一个通向登录页的“个人中心”链接，误判已登录比“不明确”更坏。名字要求整体匹配也是故意的：裸“退出”是退出按钮，“退出全屏”是退出全屏按钮，子串匹配会把视频播放器认成已登录；整体匹配认不出来时只会退回“不明确”，不会误判。

见 [2026-11-27-browser-cookie-import.md](../feature/2026-11-27-browser-cookie-import.md)（它引入了 `isLoginPage` 与 Cookie 失败提示，本次是其正向补全）。

## Alternatives considered

- **在 `browser_navigate` 的工具描述里加一行指引（任务里的选项 b）** — 最强的理由：在模型调工具前就立规矩，比事后提示更直接。否掉：该描述有 300 字符上限（测试强制），现有文案只剩约 8 字符余量，加不进一句有用的话；且导航结果里的提示已在关键时刻带了同一句话，静态描述属于重复。
- **把个人中心/账号链接也算作已登录信号** — 最强的理由：有些站只挂个人中心、不挂退出按钮，多认一种信号覆盖面更大。否掉：未登录页面也常挂这类链接（点进去才是登录页），误判已登录会让机器人跳过必须的登录；认不出来只退回“不明确”，代价是多一步判断，安全得多。
- **退出名字用子串匹配** — 最强的理由：写法简单，不怕站点在名字前后多加符号。否掉：“退出全屏”这类按钮会被认成退出登录；整体匹配认不出来时只退回“不明确”，不会误判。
- **用电脑截图判断登录态** — 最强的理由：截图是最终画面，布局变了也能看。否掉：快照树里本来就有控件信息，截图往返正是这次要省掉的慢步骤；截图只留给用户看画面和真正需要看画面的任务。

## Consequences

- 注入 Cookie 后登上的导航，同一条工具结果就把登录态说清楚了：模型不用再为确认登录多调快照、不用再用 shell curl 复核，登录验证少走几步。
- 看不出结论的页面与原来完全一致；失败提示不变且优先；Cookie 注入、登录流程、computer 镜像一概不动。
- 只有服务端 adapter 改动，不需要重建 computer 镜像；随服务端部署生效。
- 测试：新增 4 个（`isSignedInPage` 已登录/未明确两组、`browser_navigate` 已登录提示、失败优先），`browser-tools.test.ts` 86 个全过，相关文件（页面浏览器工具、卡片填充、控件）58 个全过。
- 未做的事：未做真实登录端到端验证（需部署后跑一次真实登录核对）；shell curl 复核是模型行为，本次是去掉它复核的理由、不是禁用该工具，部署后仍需看一次真实运行确认模型不再复核。
