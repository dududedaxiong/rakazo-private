# Agent Note: 分享卡与回放链接跟进：译文、点开放大、布局、二维码、自定义有效期

Status: implemented

## Problem

分享功能上线后，用户在手机上发现五处问题：译文做的分享卡还是原文；分享卡预览里的图片要点开看大图；分享对话的对话框在手机上布局不协调；回放链接想要二维码，扫一下就能在另一台手机上打开；回放链接的有效期只有固定几档，想要自定义天数。

## Decision

同一轮跟进，五项都落在分享卡与回放链接上，沿用 [对话分享：分享卡与回放链接](./2026-11-16-conversation-share-cards-replay-links.md) 的实现，不改已定的版式、脱敏与链接机制。

- **译文进卡片**：core 的 `shareCardContentFromMessage` 加可选的 `textOverride: { text, model }`。用户从一条正显示译文的回复做卡片时，卡片正文用译文，仍走同一道尾标切分与脱敏；页脚模型名用翻译模型。提问、图片与视频、问题开关都不变。网页由 `useMessageTranslation` 暴露 `shareOverride`，打开分享卡的那一刻带上；手机由消息行把翻译结果带进分享动作，经 thread-screen 传给 ShareCardSheet。快照不动：快照是对话的忠实记录（v:2），翻译是各人阅读时的显示状态，回放页仍显示原文；卡片是用户按眼前所见亲手做的成品，所以卡片取眼前文字。
- **点开放大**：core 加 `shareCardMediaRect(plan, 自然宽高)`，由版式与图片自然尺寸算出画中图片的实际矩形，网页与手机共用。网页对话框点画布时只有命中矩形才打开；放大的图是图片本身（图片用原图，视频用截到的封面帧），不是放大整张卡片。手机同样用矩形判定，点中后在本 sheet 内全屏看图。图片区域右下角一个小放大标记，不加说明文字。手机全屏用 Modal 而不用查看器路由：视频封面帧没有 artifactId；Modal 内无分享动作，不触发查看器注释里记的分享取消后黑屏的坑。
- **对话框布局**：根因在最新链接行：被截断的 URL 是 nowrap，min-content 就是整条 URL 近 600px；对话框是 grid、隐式列是 auto，列被撑到 600px，所有子项跟着变宽——说明文字不换行、按钮内容看着偏右。修法是给带截断内容的两个 grid 子项加 `min-w-0`（最新链接行与列表容器），不改共享 Dialog。390px 下用真实编译样式渲染复现并确认修好：描述换两行、按钮内容与对话框同心、长标题也截断。
- **二维码**：网页对话框新建链接下方放二维码，`qrcode` 库客户端生成，编码的就是显示的那条完整链接（含 token）。手机 sheet 不做：手机有系统分享，扫码需求在网页对话框上。
- **自定义有效期**：RPC 的 `expiresInDays` 从 `1 | 7 | 30 | 365` 枚举放宽为 1–365 的整数，null 仍为永不过期；上限 365 与管理端已有的一致。服务端按天数算过期时间，不变。网页与手机在原 pills 行加「自定义」与天数输入，非法输入不让创建。

## Alternatives considered

- **译文直接读消息上保存的译文**：最省事；但刚翻完还没重载时消息上没有，修不到用户当场遇到的情况，否掉。
- **快照里带译文**：回放页也能显示译文；但要升快照版本、改回放页，翻译是显示状态不是对话内容，否掉。
- **放大整张卡片**：实现最简单；但用户要看的是图本身，放大卡片看不清图，否掉。
- **点画布任意处都放大**：不用算矩形；但点文字也会跳大图，误触多，否掉。
- **改共享 DialogContent 的列定义**：根治所有对话框；但影响全部对话框，只修出问题的两个子项更稳，否掉。
- **二维码服务端生成**：不用引库；但链接在客户端已完整，客户端生成不走网络，否掉。
- **有效期精确到小时或分钟**：更灵活；但链接有效期按天已够，服务端只接受天数，否掉。
- **手机也做二维码**：与网页一致；但手机有系统分享，扫码需求在网页对话框上，否掉。

## Consequences

- **收益**：译文卡片显示译文；图片点开看大图；对话框在手机上不再溢出；链接可扫码；有效期可自定天数。
- **代价与已知上限**：卡片页脚的模型名在译文卡上是翻译模型，不再是原回复模型；二维码只在网页新建链接时出现，列表里的旧链接没有；自定义有效期只精确到天；快照与回放页仍只含原文。
- **App 端**：译文进卡片与自定义有效期与网页同套 core 逻辑；点开放大在手机 sheet 内全屏看图，不走按 artifactId 取图的查看器（视频封面帧没有 artifactId，卡片手里只有 data URL）。

- 网页全套件：255 文件、2325 通过、1 失败——`i18n-catalog.test.ts` 要求波兰语每条都有译文，而 `1 year` 的波兰语在改动前已是空的，与本次无关，未修。
- 手机全套件：347 文件、4164 通过、20 失败——全是改动前已有的三处漂移，本次没动那些文件，未修：`i18n.test.ts`（两条 Groq 语音文案缺非中文翻译）、`voice-settings.test.tsx` 18 个（`voice.tsx` 用了 `serverProviderOf`，测试的 mock 没提供）、`model-settings.test.tsx` 1 个（供应商顺序期望与实现不一致）。

- 未实测：真机上的点开放大、二维码扫码、自定义有效期端到端、回放链接在真机上创建。

## 撤销后删除（第二轮跟进）

### Problem

已撤销的链接只能恢复，不能从列表里去掉；用户想要撤销之后能彻底删除。

### Decision

- 服务端新增 `shares.delete`：按 id 删行，沿用 revoke 的 `requireShare` 验权（只认自己的 thread）。删行后按 page 链接删除的现成做法，同时删掉密钥行，并在提交后尽力从 secret store 里忘掉密封 token——链接在行删掉的那一刻就已失效，store 忘不掉也只记日志。
- 只对已撤销的链接露删除入口：网页对话框与手机 sheet 都在「已撤销」行上恢复按钮旁加「删除」，生效中仍只有撤销；过期链接不加——用户只说了撤销后删除，过期链接仍可恢复，是否也加删除是另外的决定。
- 删除是破坏性操作，要二次确认：网页用现成的 `ConfirmDialog`（标题「删除链接」，说明是该链接的标题，确认按钮 destructive）；手机用原生 `Alert.alert`（标题复用已有的 `Delete {name}?`，取消/删除两钮），与删除提示词预设的做法一致。
- 服务端不额外校验「必须已撤销」：revoke/restore 本来也不校验状态，删除只认归属；界面把入口收在已撤销行上就够了，删一条生效中的链接与「先撤销再删除」结果一样。

### Alternatives considered

- **只删行、不动密钥**：少两步；但密封 token 与密钥行会一直留在库里，链接已死却留着能开链接的凭证，否掉。
- **服务端只许删已撤销的**：更贴用户原话；但与 revoke/restore 不校验状态的做法不一致，且删生效中的链接等于撤销加删除，并无害处，否掉。
- **过期链接也加删除**：与已撤销一样是死链接；但用户没提，过期链接恢复后还能用，是否可删是另外的决定，否掉。
- **删除不确认、点一下直接删**：少一步；但删除不可恢复，误删没有补救，否掉。
- **网页自己写确认框**：不用引组件；但 `ConfirmDialog` 已有，复用更稳，否掉。

### Consequences

- **收益**：已撤销的链接可以从列表里彻底去掉；链接的行与密封 token 一起清掉，不留死凭证。
- **代价与已知上限**：删除不可恢复，删错只能重建链接（新 token、新链接）；过期链接仍只能恢复，不能删除；手机删除确认复用 `Delete {name}?`，标题里带的是链接标题。

### Verification

- `conversation-shares.test.ts`：删已撤销的链接——行、密钥行、store 里的密封 token 都清掉，返回 `{ ok: true }`；别人的链接 revoke 与 delete 都拒绝。
- `shares-rpc.test.ts`：`shares.delete` 只接受 `{ shareId }`。
- 手机 i18n 全量扫描：新串 `Could not delete the link` 已进 8 个语言目录；确认标题与按钮复用已有串。
- 网页跑 `lingui extract` 补 2 条新串（`Delete link`、`Could not delete the link. Try again.`），zh-CN 与 zh-TW 已填。
- 未实测：真机上的删除流程。

## 点已有分享出二维码（第二轮跟进）

### Problem

回放链接的二维码只在新建链接时出现；列表里已有的链接要点开才能扫码，用户想点哪条就扫哪条。

### Decision

- 网页与手机的链接列表行都可点：点行展开该链接的二维码，再点同一行收起；只同时展开一条。码与新建时同一套：网页复用 `shareLinkQrDataUrl`（PNG data URL，192px），手机新加 `shareLinkQrSvg`（同一 `qrcode` 库的 SVG 串，`SvgXml` 192×192 画出）。
- 行里的按钮不触发展开：网页四个按钮（复制/恢复/删除/撤销）的 onClick 都 `stopPropagation`，键盘在行本身上按 Enter/空格才展开（焦点在按钮上时不展开）；手机行内按钮是内层 Pressable，点按钮只走按钮。
- 手机要新引 `qrcode`：手机之前没有二维码生成能力，`react-native-svg` 已有。`qrcode` 的 SVG 输出是纯 JS 串，不用 canvas；手机版只加 `qrcode@1.5.4` 与 `@types/qrcode@1.5.6` 两个依赖（与网页同版本），lockfile 里复用网页已有的包记录，只补 mobile 的 importer 两行。
- 没有新文案：二维码旁不加说明文字；手机确认与报错复用已有串，网页也没有新串，所以不用补翻译。

### Alternatives considered

- **列表每条都常驻二维码**：不用点；但每条 192px，列表很长且大部分时候用不上，否掉。
- **手机用 PNG data URL + Image**：与网页同一份 helper；但 RN 的 Image 播 data URL 的 PNG 要走原生解码，不如 SVG 串直接画，且 `qrcode` 的 SVG 输出本来就是纯 JS，否掉。
- **二维码服务端生成**：手机不用引库；但上一轮已定客户端生成不走网络，链接在客户端已完整，否掉。
- **点行直接打开回放页**：少一步；但用户要的是扫码给另一台手机看，不是自己打开，否掉。

### Consequences

- **收益**：列表里任何一条链接都能点开扫码，与新建时同一只码；手机也有了二维码，不用回网页。
- **代价与已知上限**：手机多了 `qrcode` 一个依赖；已撤销链接的二维码照样显示（码就是那条链接，链接本身已失效，复制按钮也是如此）；二维码生成失败时行只是什么都不展开，没有报错文案。

### Verification

- `share-link-qr.test.ts`（网页）与 `share-link-qr.test.ts`（手机）：同链接同码、不同链接不同码；网页出 PNG data URL、手机出 SVG 串。
- 手机 i18n 全量扫描：本次没有新串。
- 未实测：真机上点行出码、扫码打开。
