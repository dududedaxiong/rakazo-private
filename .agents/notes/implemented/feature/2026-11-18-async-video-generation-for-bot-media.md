# Agent Note: 机器人视频模型走异步视频生成接口，不走聊天接口

Status: implemented

## Problem

机器人配的视频模型走聊天接口出视频：测试与聊天都调 `chat/completions`，指望回复里带回视频链接。但视频生成模型本身是异步任务接口：提交只返回任务号（`PROCESSING` / `SUCCESS` / `FAIL`），结果要另外查。测试时上游直接报不支持同步调用方式，这不是测试按钮的毛病——聊天里走同一条路，也会报同一个错。

2026-11-18 真聊天实测确认了第二点：机器人根本没调配好的视频工具，而是自己去机器上写脚本直调视频接口，模型名还用错；任务建了但轮询卡在排队，最后自写一句“视频生成完了”就断了，附件没挂上。工具链路不通时，聊天模型会自己瞎折腾而不是报错——修通工具是根，单靠改提示词拦不住。

还有第三点：后台轮询只认全局视频提供方。`pollMediaVideo` 与 `reconcileMediaVideos` 都在全局提供方没有视频能力时直接返回，而本部署没配全局提供方。所以即使提交端改成异步返回排队任务，后台也不会去查它，视频永远到不了对话。轮询必须按任务所属的机器人重新解析提供方，而不是只用全局那一个。

## Decision

机器人视频模型走与供应商无关的异步视频生成适配，复用已有的提交 + 轮询形态：

- **提交**：向同一连接的 `videos/generations` 发提示词与模型名，拿回任务号；密钥与地址复用该连接已有的配置，不另加供应商专属环境变量。
- **轮询**：按任务号查该连接的通用异步结果接口 `async-result/{id}`，直到 `SUCCESS`（取 `video_result[0].url` 并下载）或 `FAIL`；轮询间隔与超时复用现有的视频轮询机制（提交后即返回任务、后台轮询、超时失败不悬着）。
- **接入点**：机器人视频模型先走现有聊天接口；只有当上游明确报不支持同步调用时，才切到异步视频接口提交。这样聊天模型仍走老路，只有视频生成模型走新路；异步提交失败时，仍按现有顺序试下一个备选模型。
- **同步被拒的判定**：同步调用的上游报错正文里带有同步调用被拒的信号时，媒体层把它归类为独立的错误码 `async_required`，视频重试只认这个码、不在提供方里做字符串匹配。
- **结果形态**：复用现有的视频任务（提交返回任务号、轮询返回完成或失败、完成时带视频字节），不另造一套任务模型；前端已有的“正在生成”状态直接复用。
- **任务号**：机器人提供方返回的任务号是 JSON，带版本号、模型名与上游任务号；轮询时按模型名找回同一条调用，再查上游。机器人改配置删掉该模型后，未完成的任务按失败收尾，不静默悬着；无法解析的任务号交给回退提供方，与旧行为一致。
- **轮询解析提供方**：后台查视频任务时，先按任务所属的机器人重新解析它的媒体提供方（全局提供方只作回退），再调 `pollVideo`；找回任务的 reconciler 不再只认全局提供方有视频能力。解析只用连接解析本就需要的那几项（数据库、密钥存储与可选的部署模型输入），不把整个执行器依赖拖进后台任务。
- **测试按钮**：视频测试也走异步链路——提交一次真实的短视频任务，短暂轮询；任务被接受即判为支持，轮询到完成或超时都如实报告，不把“还在生成”当成失败。

已核对的接口形态（2026-11-18，文档为准）：提交 `POST {base}/videos/generations`，`{model, prompt}`，返回 `{id, task_status}`；查结果 `GET {base}/async-result/{id}`（该连接的通用异步结果接口，不是 `videos/generations/{id}`），`task_status` 为 `PROCESSING` / `SUCCESS` / `FAIL`，成功时 `video_result[0].url` 为视频地址（约 24 小时有效）、`video_result[0].cover_image_url` 为封面。

## Alternatives considered

- **什么都不做，等用户在聊天里试一次** — 零成本，能拿到一次实测失败；但测试与聊天走同一条代码路，结果可预见，试只是把同一个失败再看一遍。
- **只修测试按钮，让测试也走异步** — 测试能通过；但聊天仍走同步调用，用户真正要视频时还是失败，修的是表象。
- **只给这一个供应商写专用适配** — 最快；但供应商名会漏进共享契约与设置，违反“供应商只出现在适配层、能力走通用接口”的规矩，下一个同类供应商还得再写一套。
- **复用现有的 fal 队列协议** — 提交 + 轮询的形态现成；但 fal 的队列地址与状态字段是 fal 自家的，与 OpenAI 兼容的视频生成接口不是同一套协议，直接复用对不上。
- **提交时直接在工具调用里轮询到完成** — 不用改后台轮询；但视频生成要几分钟，工具调用会把整轮对话拖死，超时与重试都难收尾。提交即返回、后台轮询是已有的形态，不另起一套。
- **把连接密钥放进任务号，让全局提供方直接轮询** — 轮询不用再解析机器人提供方；但密钥会以明文落进任务行（数据库、日志、备份都看得到），与密钥只存加密存储的规矩冲突。轮询时重新解析提供方多一次数据库查询，换回密钥不落地。
- **视频一律走异步，不再先试聊天接口** — 少一次失败调用，逻辑更直；但能走聊天接口直接回视频的模型会被迫多等一次异步任务，改了现有行为。先试同步、被拒再切异步，只给走不通的模型换路。

## Consequences

- 聊天里要视频时，异步视频模型现在能出片：提交后对话显示正在生成，后台轮询完成后把视频贴进对话并给机器人一次跟进回合。
- 视频测试按钮不再对异步模型报“不支持同步调用”；一次测试提交一次真实的短视频任务，按次计费的提供方上每次测试扣一次费用，与生图测试一致。
- 任务号是落盘格式（任务行里存着）；旧任务号无法解析时交给回退提供方，与旧行为一致，不静默重提。
- 异步提交成功的切换时间线不带到完成消息上：排队任务的结果里不存切换记录，完成时只标当前模型；与全局提供方的排队任务一致。
- 轮询失败只重查、不重提；提交带去重键，重复提交不重复扣费。
- 聊天模型与生图模型的链路不受影响。

## Testing

- 离线测试覆盖提交、轮询中、成功、失败四态：提交返回任务号、轮询 `PROCESSING` 报运行中、`SUCCESS` 取视频地址下载、`FAIL` 报失败、无 `task_status` 报上游失败；同步调用被拒只在视频模型上报 `async_required`，生图模型仍报上游失败。
- 机器人提供方测试覆盖：同步被拒后切异步提交并返回排队任务、轮询到完成挂上视频与模型名、异步提交失败时试下一个备选模型、轮询一个已删模型时按失败收尾。
- 视频测试按钮测试覆盖：同步被拒后走异步提交、提交后立即完成报返回视频、提交后仍在生成报任务已提交正在生成。
- 相关测试全过：`bot-media-generation`、`pi-openai-compatible-provider`、`media-generation-provider`、`media-generation-tools`；后台轮询的 Postgres 测试需数据库，未在本地跑，靠部署后的真聊天验证。
