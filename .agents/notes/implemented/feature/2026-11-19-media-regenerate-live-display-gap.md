# Agent Note: 媒体重新生成进行中提示与完成结果实时显示

Status: implemented

## Problem

图片重新生成已改异步（见[双模式异步重新生成](2026-11-19-media-two-modes-async-regenerate.md)）：点随机生成后服务端提交即回，生成完由后台轮询送达。网页端两次实测对照：

- 第一次点随机生成：新图约 2 分钟内在页面实时出现，正常；但「正在生成图片…」进行中提示全程没有实时出现过。
- 第二次点随机生成：3 分钟内页面什么都没出现——无新图、无进行中提示、无报错，侧栏 Working… 约 30 秒消失。但服务端证据完整：任务 30 秒内完成，新图文件已入库，图片消息与跟进文字都已写入数据库，进行中提示事件在提交后 5 毫秒即落库，全部 run/task 零报错。
- 完整刷新后，第二次的新图与跟进文字都出现了：丢失在落库到前端实时显示的最后一公里，不是渲染失败。

进行中提示两次都没实时出现（事件两次都落库了），且提示是瞬态的、刷新找不回来，所以它的问题与新图消息的问题要分开修：提示只能在 run 进行中显示出来，消息则必须在完成后可靠出现。

## Root cause

### 进行中提示：媒体 run 从不宣告自己开始

服务端在提交时只追加了一个 `thread.progress` 事件（payload 为进行中文字加 `activity: true`），但从来没有为这个 run 追加 `run.started` 事件。数据库事件表可以证明：媒体 run 只有 progress、消息创建与跟进 run 的终态事件，没有自己的 `run.started`。

网页端把一个 run 认作“进行中”只通过三条路：收到 `run.started` 事件、快照里 `activeRuns` 包含它、或是发消息的回执。重新生成三条路全断：没有 `run.started`；实时订阅阶段客户端不拉快照，30 秒左右的 active 窗口内没有任何快照能把该 run 带进 `activeRuns`；也没有发消息回执。

于是两条渲染路都闭合了：

- 气泡：`activity: true` 的 progress 块按设计属于工具活动块，永不渲染成气泡（工具活动只在状态行显示）。
- 状态行：工作标签只在 `running` 为真时渲染，而 `running` 取自快照的 `activeRuns`——媒体 run 从没进去过，所以标签从不出现。

这就是提示两次都没出现的原因：不是事件丢了，是事件到了也没有能显示它的位置。

### 完成消息：终态刷新是一次性的兜底，没有重试

完成的图片与文字靠两条路进页面：实时流的 `thread.message.created` 事件，或 run 终态事件触发的快照重拉。重拉是单次的：失效合并器消费掉那一次失效后，若那次重拉失败（快照请求有 2 秒超时）或结果被丢弃，不会再有第二次；重放阶段里，已见过的事件不再触发副作用，所以终态事件的重放也不会再触发重拉。run 终态后不再有新事件，页面就一直停在旧快照上，直到用户手动刷新。

侧栏 Working… 消失不能证明实时流工作过：侧栏是独立的 3 秒轮询，与对话的实时订阅无关。

## Decision

已按以下两处改动，各负责一类事件：

### 1. 服务端：给媒体 run 一个完整的生命周期开头

在重新生成提交处，创建 run 之后、追加 `thread.progress` 之前，先追加 `run.started` 事件（payload 与执行器一致：`trigger: "media"`，`routineId: null`），同样 fire-and-forget、失败不阻塞提交。提交失败分支里 run 被标失败后，再追加 `run.failed`（payload 为 `{error}`，与终态事件的形状一致）。

这样客户端收到 `run.started` 就把 run 登记进 `activeRuns`：进行中提示立刻有地方显示（工作标签读到 progress 文本），重新生成按钮在 run 进行中保持禁用（它本就依赖 `transcriptRunning`），语音头像等活动指示也一致。

### 2. 客户端：媒体 run 开始后做有界快照对账

订阅的 `onEvent` 收到 `trigger` 为 `media` 的 `run.started` 事件时，为该会话启动一次单飞行的对账循环：每 2 秒重拉一次快照；每次重拉后读已提交快照的 `activeRuns`，没有进行中的 run 就停；超时 10 分钟停；订阅结束（切会话、卸载）时停；新的媒体 run 开始时，旧循环停掉、新循环接管（同一会话只跑一个）。

对账循环覆盖两类事件：进行中，循环拉到的快照自带该 run 的 `thread.progress` 事件（快照查询本就包含进行中 run 的 progress 事件），提示即使实时流漏了也能在 2 秒内出现；完成后，循环拉到的快照自带新图消息与跟进文字，run 终态即停，不再多拉。重拉走已有的快照刷新合并器，并发重拉会合并成一次。

沉降处的终态事件本次不补：跟进 run 的终态事件与对账循环的快照已经能传达沉降；为一个冗余事件放宽后台轮询的事件依赖（只给了 `notify`，没有 `append`）不值得。

## Alternatives considered

- **沉降处也补 `run.completed` / `run.failed` 事件**：最强理由是生命周期对称，客户端能立刻清掉工作状态。否决：跟进 run 的终态事件与对账快照已经传达沉降；后台轮询模块的依赖只给了事件通知没有事件追加，放宽它要改工作线程的组合根与全部沉降调用点，为一个冗余事件不值得。
- **订阅重放进入 live 阶段时重拉一次快照**：最强理由是改动点单一，且能补上被抑制的终态刷新。否决：只在流送达过事件时才生效，流完全断开时帮不上忙；且每次打开会话、每次重连都会多一次快照拉取，影响所有会话，不只重新生成。
- **从重新生成按钮处轮询**：最强理由是触发点精确（只在用户点了之后跑）。否决：要给三个层级的组件新加一个回调 prop；从 `run.started` 事件触发能覆盖同一会话里任何来源的媒体 run（包括提交失败分支），且不需要改组件接口。
- **把媒体 run 走 `finalizeRun` 沉降**：最强理由是复用执行器的终态路径。否决：那条路径要求 lease/attempt 并写一条回复消息，媒体 run 没有 lease、也不产生自己的回复文本，硬套会改掉它的“无 lease、不被 run 协调器认领”的设计。
- **什么都不做，只依赖终态刷新**：最强理由是改动为零，第一次实测里消息就是这么实时出现的。否决：终态刷新单次、无重试，第二次实测已经证明它会漏；进行中提示则完全没有修复路径。

## Consequences

- 点随机生成或细节修改后，「正在生成图片…」/「正在生成视频…」在 run 进行中出现：实时流正常时由 `run.started` 立即带出，流漏了时对账循环 2 秒内补上。
- 生成完成的新图与跟进文字不依赖手动刷新出现在对话里（对账循环拉到的快照自带）。
- run 进行中时重新生成按钮保持禁用；run 沉降后不残留 Working… 状态。
- run 沉降或超时后对账循环停止，不再产生快照请求；切换会话、关闭页面时循环停止。

## Testing

- `apps/api/src/routes/media.test.ts` 15/15：提交时 `run.started` 在 `thread.progress` 之前落库；提交失败时补 `run.failed` 且不调度轮询。
- `packages/core/src/thread-subscription.test.ts` 50/50：对账循环终态即停、超时即停、中止即停、重拉失败重试。
- `apps/web/src/pages/shell/use-thread-sync.test.tsx` 12/12：只有 media 的 `run.started` 启动看护，非 media 不启动，同会话重复不重复启动。
- 网页端到端验证待部署后做：点随机生成，盯「正在生成图片…」与新图实时出现，复测两次。

## Risks

- 每次重新生成在 run 进行中每 2 秒多一次快照拉取（图片约 15 次，视频约 60 次），10 分钟封顶；重拉走已有合并器，并发请求会合并。
- `run.started` 事件会进入分析采集（与聊天 run 相同），无新增隐私面：事件只含 run 标识与触发类型。
- 对账循环的触发依赖 `run.started` 事件送达；实时流在提交瞬间完全断开是残留风险——那时所有实时更新都停，不只重新生成，需另外修订阅本身。
