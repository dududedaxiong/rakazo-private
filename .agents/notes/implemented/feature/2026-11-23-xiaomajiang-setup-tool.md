# Agent Note: /p666 一键安装小码酱的服务端工具

Status: implemented

## Problem

小码酱要进 Rakazo：一个“小码酱助手”人设模板（全文约 22,411 字符）、一个专用空间、一个同名机器人、23 个技能，且技能只在专用空间可见。模板创建/应用、技能收范围这两样没有对应的 agent 工具，只能走网页端；提示词与技能正文又不能以明文经过仓库、聊天记录或工作区文件。

## Decision

新增一个服务端工具 `xiaomajiang_setup`，描述里写 `/p666`。Telegram 的斜杠命令会被原样转发给 agent 当普通消息，模型看到 `/p666` 就调这个工具，不调别的。

工具 handler 在服务端跑，全程不经过模型手里的明文：

- 口令只从环境变量 `XIAOMAJIANG_PASSPHRASE` 取，缺失直接拒绝，不做任何写操作。
- 密文包从 `XIAOMAJIANG_BUNDLE_FILE` 指定的文件读，默认先找镜像根目录下的 `xiaomajiang.enc`，再找随镜像带进来的仓库内副本。找不到包也直接拒绝。
- 密文格式与已验证的混淆包方案同款：PBKDF2-HMAC-SHA256（20 万次）派生密钥，HMAC 流密码异或，先验签再解密；口令错、密文被改、格式错都抛错，不落明文、不带回退。
- 解开后的载荷只做形状校验（模板正文非空且不超过 30000 字符；技能是非空数组，每篇都能过既有的 SKILL.md 校验），然后直接调内部服务：模板按名 upsert、空间按名找或建、机器人在新空间里找或建并应用模板、技能逐个找或建。技能建在家空间就是专用空间、默认不对所有空间开放，所以不需要再调范围接口；跨空间重名的旧技能则按既有收范围逻辑挪进专用空间。
- 整个安装幂等：重复发 `/p666` 只会复用已有的模板、空间、机器人与技能，不会建出第二份。
- handler 最后只回一句话摘要，聊天里不落任何提示词或技能正文。

打包脚本 `scripts/build-xiaomajiang-bundle.mjs` 在口令所在处跑：按钉住的上游版本取回两篇提示词与 23 篇技能，逐篇核对名字，把简介换成 4–8 字的短版，拼好模板正文后加密成单行密文并当场自验；只输出路径、字节数与篇数，不打印任何内容。生产密文包由部署方在服务端现场打包，口令只放服务端环境变量，不进聊天、不进仓库。两个环境变量（口令与包路径）都已声明进三个 compose 文件的 `x-app-environment`（compose-env 测试会强制同步）；口令还进了 `turbo.json` 的 `globalPassThroughEnv`，否则 Biome 的 noUndeclaredEnvVars 会告警。

## Correction 2026-11-23（打包脚本取件路径）

- 钉住版本 e2ff5c82 的上游树里，提示词与技能不在仓库根目录，而在 `dsh-purge-plugin/` 前缀下（`dsh-purge-plugin/prompt/*.md`、`dsh-purge-plugin/skills/*/SKILL.md`，共 77 条、23 篇技能，名字与清单逐一对过）。脚本最初只认根目录路径，2026-11-23 晚在 cue 上跑时取到 0 个技能、直接退出，未产包、未动 .env、服务未受影响。
- 修正：脚本加 `UPSTREAM_PREFIX = "dsh-purge-plugin/"`，清单过滤、存在性检查与取件都走带前缀的路径；其余逻辑（清单核对、简介短版、加密、自验）不动。
- 另：部署容器里 `/app` 不是挂载卷且不可写，生产包不放 `/app/xiaomajiang.enc`；改放 api 唯一挂载卷 `/data/xiaomajiang.enc`，用 `XIAOMAJIANG_BUNDLE_FILE=/data/xiaomajiang.enc` 指过去。compose 文件的 `x-app-environment` 里两个变量本来就有声明，部署时要核对 cue 上那份 compose 副本是否同步，缺了就补。

## Correction 2026-11-24（/p666 触发要补系统提示词一句）

- 2026-11-24 00:08 真机实测：对 New Bot 发 `/p666`，机器人回 “I don't recognize "/p666"”，只认 /menu、/model、/pmodels、/ptest。包、口令、部署都没问题，问题在触发层。
- 根因：`xiaomajiang_setup` 不在 `CORE_BUILTIN_TOOL_NAMES` 里，是延迟工具——模型平时只看到 `find_tool`/`use_tool`，工具本身的描述（写了 /p666）藏在目录后面；系统提示词里 /pmodels、/ptest、/menu 都有 `offeredBuiltinClause` 一句把命令绑到工具，/p666 没有这一句，模型就按“未知命令”回了。
- 修正：按 /pmodels 同款，在 `run-instructions.ts` 的命令句组里加 `offeredBuiltinClause` 一句（`/p666` → `xiaomajiang_setup`，回摘要原文）。工具本身不进核心列表，提示词只在工具可用时出现。

## Alternatives considered

- 提示词级方案（在管理 bot 的人设里加一条规则，遇 `/p666` 就用现有工具装）：最强的理由是不改代码；没用，22KB 提示词与 23 篇技能正文要过聊天记录，与混淆要求直接冲突；模板创建与技能收范围也没有工具，只能走网页端；装成什么样全看模型发挥。
- 明文包进仓库、handler 直接读明文装：最强的理由是实现最简单，不用加密；没用，提示词与技能正文会以明文落在仓库与聊天记录里，违反用户“过不了审就混淆”的要求。
- 复用另一端网关的插件机制：最强的理由是现成；没用，Rakazo 没有往系统提示词插插件段的机制，插件装不到 Rakazo 里。
- 把工具放进显式审批集：最强的理由是大副作用应由用户确认；没用，用户明确要求 `/p666` 输入即办；口令本身就是门禁，工具只动调用者自己的账号、且幂等，再加一层确认等于把口令触发变回两步。所以工具不在审批集里，默认不弹审批。

## Consequences

- 收益：`/p666` 一句话装好小码酱全套；提示词与技能正文在流转中始终是密文；重复触发安全；其他机器人与空间不受影响。
- 代价：密文包与口令是两个分开的人工步骤——包要在服务端现场打包，口令要放进服务端环境变量；两者缺一个，工具就拒绝工作。包里内容有变要重新打包。
- 边界：工具只解决安装；技能正文引用的原平台路径与配置在 Rakazo 沙箱里不存在，装完能调出来，不等于按正文能干活，逐篇改写是另一件事。
- 风险：工具默认不弹审批，任何能给机器人发 `/p666` 的用户都能触发安装；但安装只动调用者自己的账号，且幂等，不会扩散到别人的空间。
- 待定：打包脚本要从上游取回钉住版本的内容，本地试取时触发过一次执行风险检查而停手，未做 checkout、未复制文件。生产包的打包动作本身须由部署方确认后再在服务端跑，本工具的代码与测试不依赖那份内容。
