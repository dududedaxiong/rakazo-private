# Agent Note: 网页第五批：报错说人话、密钥巡检、切换过渡提示

Status: implemented

## Problem

用户 2026-11-15 点头的第五批（3 项），实现进度一直没核实过：

1. 报错说人话：模型/调用报错时给用户看得懂的中文提示，而不是原始错误码/堆栈。
2. 密钥巡检：零 token 巡检供应商密钥（只调模型列表接口验 key，不耗 token），死 key 在提供方列表标红。
3. 切换过渡提示：模型卡住自动切备用时，显示一行"正在切换"之类的过渡提示，别让切换看起来像又卡住了。

这次先核对现状再补缺：只做缺的部分，不重做已有的。

## Decision

核对结论：三项里两项已经完整实现并有测试，只有一项有个缺口，本次只补那个缺口。

- 第 1 项（报错说人话）：已实现。`packages/core/src/run-error.ts` 的 `normalizeRunError` 把 401/403/404/429/402/502/503/529/超时/断连/额度/上下文/输出失败映射成中文摘要加修复动作（`describeModelError` 再归成 `invalid_key`、`model_not_found`、`rate_limited`、`timeout`、`connection`、`quota`、`unknown` 七类）；网页 `apps/web/src/lib/run-error.ts` 的 `translateRunError` 接 Lingui 翻译，zh-CN 译文齐全；聊天（`model-error-actions.tsx`）、图片/视频（`toastModelError`）、翻译（`message-translation.tsx`）都走同一套归一化，原始错误只留在 Details 里。缺口在模型测试弹窗：`ModelHealthDialog` 把每行失败的 `row.detail`（上游原始错误，如 `Incorrect API key provided: sk-…`）直接显示出来。本次只改这一处：弹窗里失败行改成 `normalizeRunError(row.detail, translateRunError, locale).summary`，即同一套中文摘要；契约里 `detail` 的含义不动（仍是上游原始错误），改的只是网页这一处的呈现。弹窗文案与徽章（`No permission`、`Rate limited` 等）不动。
- 第 2 项（密钥巡检）：已实现。服务端 `checkModelCredentialKeyHealth`（`packages/adapters/src/pi-models.ts`）只调提供商的模型列表接口（`GET {base}/models`），不发补全请求，不耗 token；状态分 `ok`/`invalid_key`/`unreachable`/`timeout`/`unsupported`，结果持久化到连接上。网页打开模型设置页就自动全量查一次（`use-key-health.ts`），另有"Check all"重查；死 key 在提供方列表里以 `text-destructive` 红色显示 `Invalid key · 时间`（`key-health-status.tsx`）。本次不改行为，只补一个 `KeyHealthLine` 的渲染测试，把"死 key 标红"锁住。
- 第 3 项（切换过渡提示）：已实现。服务端切备用时 `executor.ts` 的 `onModelSwitchProgress` 追加 `thread.progress` 事件，文案是中文的"X 失败，正在切换到备用模型 Y…"或"X 长时间无响应，正在切换到备用模型 Y…"；快照把进行中 run 的 `thread.progress` 事件带给客户端；网页把 `progress` 块渲染成进行中的状态行（`transcript.tsx` 的 `[role="status"]`），备用模型一回话就消失，不进聊天记录。常规与后台 run 不发这条（没有 live 线程可显示），切换本身照常发生。

## Alternatives considered

- **模型测试弹窗的缺口改在服务端（建报告时就把 `detail` 归一化）** — 没选。`detail` 的契约含义就是"上游原始错误"，改它等于改跨端契约，手机端读同一份报告也会变；任务明确不动 App。网页呈现层归一化只影响网页，手机不动。
- **弹窗里原始 detail 保留，再补一行中文摘要** — 没选。两行就是多余的界面元素，违背"界面极简、不加解释性文案"的规矩；徽章已经给了失败类别，摘要给了修复方向，原始文本没有额外的行动价值。
- **弹窗里按失败状态（`limited`/`auth`/`notfound`…）直接映射固定文案，不走 `normalizeRunError`** — 没选。那是第二套分类器，会和共用的那套慢慢 drift；`normalizeRunError` 的判定（限流/密钥/额度/超时/断连）已经覆盖弹窗里会出现的原始文本，且同一套分类在聊天、图片/视频、翻译里已经在用。
- **密钥巡检改成定时后台巡检** — 没选。第五批只要求"巡检 + 死 key 标红"，打开模型设置页自动查一次加手动"Check all"已经满足；定时巡检要新增后台任务与节奏，超出本次需求。

## Consequences

- 模型测试弹窗里失败行不再出现原始上游错误；显示的是与聊天、图片/视频、翻译同一套的中文摘要与修复方向。`detail` 的原始文本仍在服务端报告里，不进界面。
- 密钥巡检与切换过渡提示零改动；本次只给 `KeyHealthLine` 补了渲染测试。
- 代价与边界：弹窗摘要用的是 `normalizeRunError` 的通用判定，个别原始文本（如只有"No permission for this model"、无状态码的访问拒绝）会落到通用句"模型提供商返回了错误。"，但徽章仍显示"No permission"，类别信息没丢。翻译/图片/视频的切换没有 live 过渡行（它们不是 live 聊天 run），只有聊天 run 有；切换完成后三者都在结果下方出切换时间线。
- 未验证：弹窗改动没截过图（本环境无浏览器截图流程）；服务端部署后才能在真机上看到。本地测试：网页模型设置文件夹 + 报错/切换相关用例 11 个文件 79 个全过（含新写的弹窗 6 个、KeyHealthLine 6 个）；core 的 run-error/user-error/model-switches 与 adapters 的 executor-backup-start/pi-runtime-fallback 共 5 个文件 436 个全过；`pnpm verify-notes` 20 篇通过；Biome 干净。
